Folio — full project review, July 2026

Scope. A whole-project review of kindle-private-cloud — the Folio Rails 8 server (server/, ~6k lines Ruby: 16 models, 11 jobs, ~20 controllers, an 18-file app/services/library layer) and the kindled Rust daemon (kindled/, ~2k lines) that runs on a jailbroken Kindle. Live at kindle.scc.im behind Traefik; single-user, self-hosted, SQLite-only, Solid Queue running inside Puma.

How this was produced. Seven independent grok-4.5 reviewer workers each went deep on one lens (Rails architecture, server security, data & performance, the Rust daemon, testing & ops, product & UX, and ecosystem positioning). Every finding was then adversarially re-checked against the actual source by a separate verification agent, and the highest-impact claims were hand-verified line-by-line. Each finding below carries that verdict: CONFIRMED matches the source as stated, PARTLY has a real kernel but a materially wrong detail (corrected inline), WRONG is contradicted by the source, and UNVERIFIED was not machine-checked (lower-severity items; treat as reviewer opinion). Grok proposed ~72 "new ideas"; those that already exist in the repo were filtered out during verification and are not presented as new.

Overall verdict

Folio is well-engineered for what it is: a thoughtful, single-purpose system with genuinely hard problems solved correctly — the 5.19 cover-tile fix (joint MOBI6+KF8 transcode), fork-safe pid-keyed SQLite handles, a byte-identical KRDS codec with round-trip tests, safe Open3 Calibre invocation, per-device send queues with an eviction planner, and a real two-way reading-position sync. The verification pass repeatedly downgraded grok's severity claims — several "critical" flags were overstated for a single-user box. The review found no remote-unauthenticated compromise and no data-loss bug in the steady state.

The real risks cluster in three places: (1) operational fragility — there is no automated backup for the SQLite set and the CI never actually runs; (2) authorization breadth — a device token reaches the whole library, not just its queue, and any web user is effectively a co-admin; and (3) scale cliffs that are invisible today but bite around a few thousand books. None are emergencies for a single-user deployment; all are cheap to fix now and expensive to fix after a data-loss scare or a library that has grown 10×.

What follows is the full register. The companion roadmap artifact sequences the fixes and the new directions into phases.

Patterns worth protecting (the roadmap should not regress these): the fork-safe pid-keyed side-DB handles; the FTS index living in its own database; argv-array Calibre invocation (no shell injection); filename sanitisation and zip-slip prevention on upload; auth rate-limiting on the web login/reset endpoints; CSRF on by default; the tight reader CSP; and the round-trip-tested KRDS codec.

1. Rails architecture & code quality

The server is idiomatic Rails 8 with good eager-loading discipline and excellent per-job error handling. The issues are about enforcement: invariants held by convention (timestamps, Ruby-only checks) rather than by the database.

High CONFIRMED Duplicate conversions can be queued for the same book/format

No DB uniqueness on (book_id, target_format). EnsureKindleFormatJob checks for an active conversion, then create!s — a classic check-then-act race two workers can both win, producing duplicate Calibre runs. A partial unique index (on active statuses) is the fix.

ensure_kindle_format_job.rb:16,22 · conversion.rb:19 (scope :active) · schema.rb:85-97 (no unique index)

High PARTLY book_files.sha256 uniqueness is enforced nowhere

Grok claimed "Ruby validation only"; verification found it stronger — there is no uniqueness at all, only validates :sha256, presence: true, and the index is non-unique. Content-level dedup is therefore best-effort. (This is partly by design — the same bytes can legitimately back two logical books — so the fix is to decide the intended invariant, not blindly add a unique index.)

book_file.rb:16 · schema.rb:60

High PARTLY Book.currently_reading issues a redundant second query

Two queries over reading_states where one window-function query would do. Verification corrected the framing: this is a fixed ~4 queries, not a true N+1, and the second fetch is not strictly redundant (it re-selects the winning rows). Real but modest; worth folding into one SQL statement.

book.rb:84-97

Medium CONFIRMED annotations.source has a default but no validation

Schema defaults source to clippings but nothing constrains it to {clippings, web}. Code branches on the value; a stray value would silently mis-route. One-line inclusion validation.

annotation.rb (no source validation) · schema.rb:30

Medium CONFIRMED Divergent conversion source-preference lists

EnsureKindleFormatJob::CONVERSION_SOURCE_PREFERENCE and Conversion::SOURCE_PREFERENCE hold different values — a maintenance trap where editing one silently diverges behaviour. Consolidate to one constant.

ensure_kindle_format_job.rb:10 vs conversion.rb:10

Medium CONFIRMED Delivery state machine is timestamp-convention, not enforced

Delivery lifecycle is computed from which of delivered_at/ evict_requested_at/removed_at are set, with no explicit status column or transition guard. It works, but nothing prevents an invalid combination. Fine for now; document the state graph or add an explicit enum before the logic grows.

delivery.rb:33-56 · schema.rb:99-111

Medium PARTLY Prepared-copy cleanup exists but the destroy hook misses one path

Grok claimed "no cleanup logic"; that is wrong — KindlePrep deletes stale prepared files on rebuild and Library.remove_book_artifacts cleans them on book destroy. The real gap (confirmed by the data lens) is narrower: destroying a single book_file removes only its original, not its prepared variant, and there is no global GC sweep. See the data-layer finding below.

kindle_prep.rb:88 · book_file.rb:101-103 · library.rb (remove_book_artifacts)

Medium UNVERIFIED MergeBooks relies on implicit cascade deletes

MergeBooks.call moves book_files then source.destroy!, trusting dependent: declarations. Adding a new association to Book without a dependent: would silently orphan rows on merge. Make the cascade explicit or add a test that asserts it.

merge_books.rb:39 · book.rb:14-19

Also flagged (lower severity): a race window inside EnsureKindleFormatJob conversion creation (same root cause as the unique-index gap); similar_books misses an includes(:book_files) eager-load; and the "device token shown in flash" item, which is really a UX/security concern (see those lenses — verification noted the claimed leak-to-URL vectors are wrong, since a flash renders in the HTML body, not the URL).

2. Server security

Realistic posture for a single-user, internet-exposed box behind Traefik TLS: no remote-unauthenticated compromise found, and several good controls are in place (safe Calibre argv, zip-slip prevention, web-auth rate limits, CSRF, host allowlist, tight reader CSP). The gaps are authorization-breadth and defense-in-depth, sharpened by the fact that Folio is deliberately not behind Authelia — its full auth surface faces the internet.

High CONFIRMED Device API file/thumbnail/state access is not delivery-scoped (IDOR)

find_book! loads any book by public_id with no check that current_device has a delivery for it. Hand-verified: BookFilesController#show calls current_device.deliveries.find_by(book:)&.update! — the &. means that when there is no delivery it simply skips the timestamp and still send_files the bytes. So any valid device token can download the entire library's files, covers, and reading-state bundles, not just its own queue. The manifest listing is correctly scoped; the file endpoints are not. Combined with plaintext token storage on the Kindle's world-readable FAT partition, a single token leak exfiltrates everything. Fix is small: scope the lookup through current_device.deliveries.

base_controller.rb:29-34 · book_files_controller.rb:3-15 · reading_states_controller.rb:8-49 · thumbnails_controller.rb:6-11 · (contrast) manifests_controller.rb:12

Medium CONFIRMED Device tokens stored and compared as plaintext

devices.token is a plaintext SecureRandom.hex(20) (160 bits — brute-force-proof, so timing-safe compare is secondary) but auth is a direct find_by(token:). A DB read, backup leak, or SQL dump yields usable credentials for every device including the synthetic web device. Hash at rest (look up by digest, show the plaintext once).

base_controller.rb:18-27 · device.rb:110-111 · schema.rb:148-152

Medium CONFIRMED No rate limiting on the device API

Web login/reset are throttled (10/3min); the device API is not. An authenticated caller can repeatedly POST up to ~20 MB reading-state bodies and 10 MB clippings with no throttle — a disk/CPU DoS against the single SQLite host. Add Rack::Attack or a Traefik rate-limit middleware on /api/v1.

sessions_controller.rb:3 · reading_states_controller.rb:5,32-34 · clippings_controller.rb:5-9

Medium CONFIRMED Any web user is effectively a co-admin

Only UsersController is admin-gated. Any authenticated user can mint long-lived device API tokens, delete devices/books, run catalog-wide Calibre jobs, and prune the library. "Invite a reader" is really "invite a co-administrator of the library and every Kindle." If multi-user is ever real, split reader vs librarian roles.

users_controller.rb:6 (sole require_admin!) · devices_controller.rb (no admin check) · catalog_controller.rb:7-47

Medium CONFIRMED Sessions never expire; admin password reset doesn't revoke them

The session cookie is cookies.signed.permanent (20-year jar) with no idle/absolute timeout. Self-service reset correctly sessions.destroy_all, but an admin resetting another user's password does not — a stolen cookie survives the password change. Add a session lifetime and revoke on any password change.

authentication.rb:41-44 · passwords_controller.rb:21-22 · users_controller.rb:29-40

Medium CONFIRMED Reader book content is still same-origin with the session

The reader applies a tight CSP (script-src 'self', no unsafe-inline/eval), which is the right primary defence and already documented as an incomplete fix by the authors. But foliate-js iframes are allow-same-origin allow-scripts and blob docs inherit the page origin, so a CSP bypass in vendored reader JS would share the app origin with session cookies. The complete fix is a separate book-serving origin.

reader_controller.rb:10-37,90-99

Medium UNVERIFIED Untrusted ebook bytes are always fed to Calibre/custom parsers

Invocation is safe (argv, no shell), but the trust boundary is wide: any uploader or anything writable under the scanned tree triggers privileged parsing (Calibre + custom MOBI/OPF/KRDS parsers) as uid 1000 with write access to storage/. Calibre has a history of memory-safety bugs on malicious documents. Low likelihood for a single-user library of self-owned books, but the mitigation (resource limits / seccomp on the conversion path) is cheap insurance.

calibre.rb:13-15,38-59 · uploads_controller.rb:10-11 · scan.rb:29-33

Medium UNVERIFIED SMTP TLS certificate verification disabled by default

openssl_verify_mode defaults to none; password-reset links travel that channel. This deploy uses protonmail-bridge on the Docker network (low practical MITM risk), but the app default is unsafe for any real remote MTA. Set verify-peer.

production.rb:72-81

Lower-severity (verification-noted, mostly opinion): enrichment HTTP client follows redirects with no host allowlist (SSRF-class, but inputs come from Open Library/Google Books, not users); no app-level upload size/count caps; device tokens shown in HTML with no rotate endpoint; generated user passwords echoed in a flash; no global CSP outside the reader; cookie secure: not set explicitly (mitigated by force_ssl); and the deliberate choice to keep Folio off Authelia — a documented tradeoff, not a bug.

3. Data layer & performance

The multi-DB layout (primary / queue / cache / cable), fork-safe handles, and out-of-band FTS DB are solid foundations. The problems are the ones that stay invisible until the library is large: no backup, full-catalog aggregates, and queue contention.

Critical CONFIRMED No automated backup or recovery path for the SQLite set

The primary, queue, cache, cable, FTS and dictionary databases are single bind-mounted files under /home/nik/folio/storage with no scheduled .backup, no Litestream, and no restore drill. A corrupt page or an rm loses the entire catalog, reading history, annotations, and delivery state. This is the single highest-value fix in the whole review. Litestream (continuous replication) or an hourly sqlite3 .backup to a second disk plus a tested one-line restore.

Absence confirmed: no litestream/.backup references in server/lib, config, app · schema files under server/db/

High CONFIRMED The Catalog page rebuilds full-catalog aggregates that don't scale

Hand-verified. LibraryScansController#show caches for only 1 minute; each miss runs BookSearch.book_ids_with_fulltext (scans length(fulltext) across the multi-GB FTS content under the process-wide mutex), Library::DuplicateGroups.count (full pluck + Ruby group_by), several full-table counts and a Solid Queue job scan. At a few thousand books this takes seconds per miss and competes for the write lock. Add a books.has_fulltext flag and counter caches so the page reads cheap columns.

library_scans_controller.rb:9-20 · book_search.rb:113-116 · duplicate_groups.rb:14-24

High CONFIRMED Cancelling the queue leaves running conversions stuck forever

Hand-verified. catalog#cancel_queued destroys queued jobs and Conversion.where(status: "pending").destroy_all, but never touches rows already in running. Since scope :active includes running, EnsureKindleFormatJob then sees a phantom active conversion and never re-queues that book. Needs a stuck-conversion sweeper (reset running rows with no live job) and to include running in the cancel path.

catalog_controller.rb:33-48 · conversion.rb:2,19,28

High CONFIRMED Full-text extraction runs on the default 3-thread queue

IndexBookJob is queue_as :default, so heavy fulltext extraction competes with everything else on the shared worker pool inside Puma, pressuring the SQLite write lock that the device API also needs. Move indexing (and other bulk jobs) to a dedicated low-priority queue.

index_book_job.rb:4

High CONFIRMED Prepared delivery copies orphaned on single-file destroy; no global GC

Destroying one book_file removes its original but not its prepared variant, and there is no periodic sweep for orphaned prepared/cover files. Over time prepared_files/ grows unbounded. Add a destroy hook for the prepared path plus a recurring GC that reconciles disk against the DB.

book_file.rb:101-103 · schema.rb:49-52

Medium CONFIRMED FTS index_book! DELETE+INSERT is not transactional

The reindex deletes then inserts without wrapping in an IMMEDIATE transaction, so a crash between the two leaves a book missing from search until the next reindex. Wrap it; consider external-content FTS to halve storage.

book_search.rb (index_book!)

Medium CONFIRMED Missing / weak indexes vs real query patterns

Several hot query paths (enrichment candidates, delivery lookups, annotation matching) lack covering indexes. Add targeted indexes matched to the WHERE/ORDER BY the controllers and jobs actually issue.

schema.rb vs controllers/services/jobs query patterns

Medium CONFIRMED Solid Queue + Puma multi-process write contention on the primary DB

Jobs run inside Puma (SOLID_QUEUE_IN_PUMA), so bulk work and web/device requests contend for the single primary-DB write lock. The repo already supports running a sidecar worker (bin/jobs); splitting the queue out is a deployment change, not new code, and is the pressure valve when the library grows.

puma.rb:38 · bin/jobs (exists)

Also flagged (lower severity, unverified): the embeddings busy_timeout (5s) is inconsistent with the 15s global policy; the scan ledger is loaded wholesale into memory each run; storage multiplies (original + converted + prepared + covers + FTS); ApplicationJob has no discard/retry policy for dead records; devices.name uniqueness isn't DB-enforced; annotation search is an unindexed substring scan; and the legacy FTS migrate path drops the category column on copy (a latent bug worth a quick check). The reviewer's ordered "what breaks first at 5k books / 3 devices": CPU wall on the single-threaded conversion queue, then disk, then catalog-UI latency, then the primary write lock — the device path stays healthy longest thanks to per-device queues.

4. The kindled Rust daemon

Compact, careful, and correct in its happy path (SHA-256 verify, atomic rename via .part, ack-after-delete ordering). The gaps are resilience under adversity: no retry backoff, no download resume, and paths from the manifest are trusted. Several of grok's "critical" flags were downgraded by verification.

High CONFIRMED Manifest item/thumbnail/removal paths are joined without traversal guards

Hand-verified. config.document_dir.join(&item.filename) (and the thumbnail and removal equivalents) trust the server-supplied filename. Rust's Path::join lets an absolute path or ../ components escape /mnt/us/documents/PrivateCloud. The server is the user's own, so this is defense-in-depth — but a compromised or buggy server could write anywhere the daemon's user can, on a device where that matters. Canonicalise and reject any path that escapes the base directory.

sync.rs:96,213,291 · api.rs:159-164

Critical→High PARTLY No retry/backoff for transient API failures

Grok flagged critical; verification downgraded it. True: no HTTP call has retry logic and a manifest-fetch failure aborts the pass. But per-item errors do not fail the whole pass, and the claimed "5-minute stall" consequence was wrong — the daemon just retries next poll. Still worth adding exponential backoff so a flaky network doesn't waste a poll cycle or hammer the server.

api.rs:127-287 · sync.rs:32,36-44 · main.rs:116

High CONFIRMED No resume for interrupted downloads

A download that dies mid-stream restarts from zero next pass (no HTTP Range resume). Fine for small books on Wi-Fi; wasteful for large files on a flaky Kindle radio. Add range-resume on the .part file.

api.rs:152-192 · sync.rs:224-234

High CONFIRMED Thumbnail paths are not validated either

Same traversal class as the manifest paths, on the cover-download path. Covered by the same canonicalisation fix.

sync.rs:291

Medium CONFIRMED SDR tar unpacking doesn't validate archive integrity or contain paths

The .sdr bundle is unpacked without integrity checks or a tar-slip guard, and not atomically. A corrupt or malicious bundle could write outside the target or leave a half-applied state. Unpack into a temp dir, validate, then atomically swap.

sdr.rs (unpack path)

Medium CONFIRMED State-file corruption silently reverts to default

A corrupt state.json is silently replaced with defaults — the daemon forgets what it has and re-downloads everything, and any un-acked removals are lost. Keep a backup chain and log loudly on parse failure.

state.rs (load path)

Medium CONFIRMED Reading-state watermark is vulnerable to clock skew

Latest-mtime-wins across devices assumes synchronised clocks. Two Kindles with skewed clocks can let a stale position overwrite a newer one. Low probability, real consequence (lost reading position). Consider a logical counter alongside mtime, or at least detect large skew.

sync.rs (watermark logic) · sdr.rs

High PARTLY Partial-download files on disk-full — corrected

Grok claimed .part files accumulate; verification found they don't (retries reuse the same path and rename on success). What's real: no disk-space precheck before a download, and no backoff on repeated failure. Add a statvfs precheck (the server already computes eviction shortfall — mirror it device-side).

api.rs:192 · main.rs:116

Also flagged (lower severity, unverified): config validation only checks SERVER_URL presence (verification noted intervals are runtime-clamped, so it's less bad than claimed); hardening-policy report assumes command availability and reports on state not command success; sidecar backup naming can collide; hard-coded clippings size limit and 1.5s catalog-refresh delay; no manifest pagination/backpressure; and a LIPC refresh called on a non-existent path. The removal ack handshake and a pre-sync disk check were both proposed as new but partially exist already (ack-after-delete ordering is correct; the server-side eviction planner covers half the disk story).

5. Testing, CI & operations

There is a real RSpec suite (~400 examples across models, jobs, requests, services) — but the CI that should guard it is misconfigured on two axes, and the ops story has the same backup gap the data lens found.

Critical CONFIRMED The GitHub Actions workflow is nested under server/ and never runs

Hand-verified: there is no .github/workflows at the repo root; the workflow lives at server/.github/workflows/ci.yml, where GitHub never looks. So CI has never run on any push. Move it to the repo root.

server/.github/workflows/ci.yml exists; repo-root .github/workflows absent

Critical CONFIRMED Even if it ran, CI runs Minitest, not the real RSpec suite

Hand-verified: config/ci.rb runs bin/rails test (Minitest) and db:seed:replant, while the actual ~400-example suite is RSpec. The green checkmark would exercise an empty Minitest scaffold. Point CI at rspec (and add the cargo tests).

config/ci.rb:11-12 · server/spec/ (rspec) vs server/test/ (minitest scaffold)

High CONFIRMED Healthchecks only prove Puma booted

/up and /healthz return 200 as long as Rails is up — they don't prove Solid Queue is processing, Calibre is present, or the SQLite write path works. Solid Queue could be dead (no conversions, no deliveries) while the container reports healthy. Add a deep health endpoint: a trivial SQLite write plus an optional Solid Queue process check.

routes.rb (/up, /healthz → rails/health#show)

High CONFIRMED No SQLite backup/restore procedure in-repo

Same gap as the data lens, from the ops angle: production DBs are single bind-mounted files with no documented backup or restore drill. Script both.

docs/kindled-operations-runbook.html (no backup section) · compose volume storage:

High CONFIRMED The conversion happy-path and Calibre wrapper are effectively untested

The most failure-prone subsystem — the Calibre CLI wrapper and a successful conversion — has no success-path spec. Add one with a stubbed Calibre that writes a temp file, so the pipeline's contract is pinned.

server/spec/ (no convert success spec) · calibre.rb

Medium CONFIRMED 7 of 10 jobs and several production controllers have no specs

Job-layer coverage is thin, and catalog, conversions, duplicates, evictions, passwords, series, sessions, uploads and the API thumbnails controller have no request specs (verification corrected one claim — library_scans is covered). Add request smoke specs for the batch/upload/auth paths.

spec/requests inventory · spec/jobs inventory

Medium CONFIRMED No kindled CI; cross-compile image unpinned; no toolchain pin

The Rust daemon has no CI, the musl cross image tag floats, and there is no rust-toolchain.toml. A silent upstream change could break the ARMv7 build reproducibly only by luck. Pin the cross image by digest and add a toolchain file; run cargo test in CI.

kindled/build-kindle.sh · Cargo.toml (no pinned toolchain)

Also flagged (lower severity): no pre-commit/pre-push hooks, no coverage reporting, no VCR/WebMock for the enrichment HTTP calls; the server/test Minitest scaffold is vestigial and creates dual-harness confusion (delete it, drop the test_unit railtie); the Dockerfile is solid but thruster is unused and specs are excluded from the image (fine); the README example count is stale and there is no deploy-rollback story; logging is STDOUT-only with no error tracking or metrics; and a spot-check of five runbook claims found them accurate against current code. Upgrade-cadence risk is moderate — an alpha sqlite-vec gem and a floating cross image are the two watch items.

6. Product & UX

The web app is genuinely nice — phone-first, live-updating, a real in-browser reader with two-way sync. The debt is in feedback surfaces: long-running operations (conversion, delivery prep) and failure states are under-communicated, and a few interactions have accessibility gaps.

Critical CONFIRMED Conversion error messages are truncated with no way to see the full output

When a conversion fails, the stored error is byte-clipped to 4000 chars and the UI shows only a fragment — the user can't see why Calibre failed or act on it. Expose the full log in a modal/drawer.

conversion.rb:37 (byteslice 4000) · books/show views

Critical CONFIRMED The reader "Preparing" state has no progress indicator or timeout

Opening a book that needs on-demand conversion shows a bare "preparing" state with no spinner, ETA, or timeout — indistinguishable from a hang. A progress indicator (even indeterminate) plus a timeout/fallback message.

reader views / reader_controller.js

High CONFIRMED Conversion failures aren't visible in the shelf view

A failed conversion is only discoverable by drilling into the book — the library shelf gives no badge. Surface a failed-state indicator on the tile.

books/index views vs conversion status

High CONFIRMED "Keep Reading" disappears when any library filter is applied

The currently-reading rail vanishes as soon as the user filters the library, losing their primary entry point. Make it persistent (or a separate, always-present surface).

books/index (currently_reading section conditional on unfiltered)

High CONFIRMED Search-mode active state isn't announced to screen readers

Toggling search mode changes behaviour with no ARIA announcement — an accessibility gap. Add aria-live/aria-pressed semantics.

search Stimulus controller / index view

Also flagged: eviction reason tokens ("finished", "dormant N days") have no tooltip explaining the criteria (verification noted the day count is embedded, so it's partial); annotation location labels read "page X · loc. Y–Z" but the unit isn't documented; the duplicates page has no sort/filter and the merge action has no conflict preview; batch catalog operations show aggregate state but no per-job progress; the FTS snippet window is small (verification corrected the misread argument — it's a 12-token window on column 6); delivery-state button labels are jargon-y; the reader loses position when switching paginated↔scrolled; the series index is text-only (no cover grid); empty states show bare command syntax; progress bars clamp to a 2% minimum (visually ambiguous at true-zero); and the reader annotation popover isn't responsive for long notes on mobile. One grok "new idea" — a reader sync-status indicator — was WRONG: the syncBanner/syncToast slots are already populated by reader_controller.js.

7. Ecosystem positioning & new directions

Folio is deliberately Kindle-native — that's its whole thesis. The ecosystem lens asks what it gives up by being only that, and where mid-2026 self-hosted reading tools have gone. The biggest openings: speak OPDS (unlock every other reader), speak KOReader's sync protocol (become the sync hub, not just a Kindle pipeline), and deepen the embeddings it already computes.

High CONFIRMED No OPDS 1.2 / 2.0 catalog endpoints

Folio's library is reachable only through its own web UI and the device API. An OPDS feed would let KOReader, Marvin, Thorium, Panels, and Calibre itself browse and pull from Folio directly — a large reach increase for a small, well-specified feature.

routes.rb (no /opds) — Folio side; OPDS 1.2/2.0 spec — ecosystem

High CONFIRMED No KOReader progress-sync (kosync) server protocol

Folio has a sophisticated two-way position sync — but only for its own Kindle path. Implementing the small, documented kosync API would make Folio the self-hosted progress-sync server for KOReader users across all their devices, a natural adjacency to what it already does.

reader_positions/reading_states — Folio side; KOReader kosync protocol — ecosystem

Medium CONFIRMED Semantic vectors ignore fulltext (shallow "meaning" search)

embed_book_job embeds only title/author/description-level text, not chunked fulltext, so "semantic search" can't find a concept buried in a book's body. Chunked fulltext embeddings + hybrid (BM25 + vector) search would make it real — and the FTS content it needs already exists.

embed_book_job.rb · book_search.rb (fulltext) — the ingredients are present

Medium CONFIRMED auto_evict can delete books from a device with no human confirm

When a device's auto_evict flag is set, a device-status POST triggers auto_evict! which queues removals automatically. Convenient, but it deletes content off the Kindle without a confirmation step. Hand-verified. Consider a "propose, then one-tap apply" default (the manual planner UI already exists) rather than silent auto-removal.

device_statuses_controller.rb:9,85 · eviction_planner.rb

Low CONFIRMED Multi-user web accounts share one global library with no ACL

All users see all books; there are no per-user shelves or visibility rules. Fine for a family sharing a library; a blocker for any wider multi-tenant use. (Same root as the security "co-admin" finding.)

books scoped globally, not per-user

Other ecosystem gaps (unverified, lower priority): no Kobo device path; Komga integration is mount-only rather than API-level (no read-progress bridge); enrichment is Open Library + Google Books only (no Hardcover/ISBNdb); no rule-based "smart shelves"; the dictionary is static offline glosses (en/it) with no vocab-notebook capture; and no social/shelf sync (Bookwyrm/Goodreads). These feed the "new directions" half of the roadmap.

Appendix — method & confidence

Seven grok-4.5 reviewers (high-judgment variant), each with a self-contained brief and read-only access, ran in parallel over the repo. Each lens's findings were piped to a separate verification agent that opened the cited evidence and returned a per-claim verdict; the security lens was re-run after its first attempt exhausted context. I then hand-verified the highest-impact claims directly against the source (device-API IDOR, manifest path join, stuck-conversion cancel, catalog aggregate query, CI location and suite, backup absence). Verification downgraded more claims than it upgraded — several "critical" flags were single-user-context overstatements — which is the expected and healthy direction. Treat CONFIRMED items as actionable, PARTLY with the correction noted, and UNVERIFIED lower-severity items as reviewer opinion to sanity-check before acting.
