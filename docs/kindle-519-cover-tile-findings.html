Kindle 5.19 cover tiles: the three conditions

Everything below was established empirically on a real Kindle (firmware 5.19.2, Photon/KPP UI) over 2026-07-11/12, via SSH: cc.db inspection, EXTH byte surgery, catalog-row diffing against store books, UI restarts, and screenshot verification after every step. A sideloaded book's Library tile shows real cover art only when all three conditions hold:

1. No store ASIN. calibre-produced MOBI/AZW3 carry EXTH 501 = "EBOK" plus a uuid ASIN in EXTH 112/113(/504). The firmware treats such files as store books: it asks Amazon for cover art by ASIN — which never resolves for a calibre uuid — caches a 5,946-byte "Nessuna immagine disponibile" placeholder in /mnt/us/system/thumbnails/thumbnail_<ASIN>_EBOK_portrait.jpg, and never extracts the embedded cover for EBOK content. Fix: neutralize the ASIN records (bump their EXTH type ids into an unknown range, +6000 — same length, no structural rebuild).
2. An explicit PDOC cdeType. Dropping EXTH 501 entirely is not equivalent: the scanner defaults MOBI6 rows to PDOC but leaves AZW3 rows typeless, and the UI renders typeless rows as text tiles even when the scanner has extracted a perfectly good thumbnail. Fix: rewrite 501's value in place — "EBOK" → "PDOC" (same 4-byte length).
3. A MOBI6 container. The 5.19 Library UI never renders cover art for KF8-only AZW3 (application/x-mobi8-ebook). Proven with a side-by-side test: the same book, same PDOC identity, same extracted thumbnail — text tile as .azw3, full cover tile as a joint MOBI6+KF8 file. Flipping p_mimeType in cc.db and restarting KPPMainApp does not help, so it is not the catalog row — the UI (or its cover pipeline) inspects the container. Fix: transcode AZW3 sources with ebook-convert --mobi-file-type both — the reader opens the KF8 half (typography unchanged), the UI sees a MOBI6 book.

Traps discovered along the way

Joint files have two EXTH blocks. A MOBI6+KF8 file carries a second MOBI header (with its own EXTH copy) in the KF8 section, and the scanner reads it: patching only record 0 produced an EBOK row from a "patched" file. The patcher must walk every PDB record and patch each one that has MOBI at offset 16.
reScanFile does not re-read metadata for existing rows. Replacing a book file in place and rescanning keeps the stale catalog identity. To re-deliver a changed file: delete the old file → rescan (row drops, the documents folder is also inotify-watched) → write the new bytes → rescan. The .sdr sidecar is keyed on the filename stem, so container swaps (.azw3→.mobi) keep the reading position automatically.
The UI caches tile bitmaps. Replacing a thumbnail file under the firmware's nose does nothing (the placeholder was also regenerated over our pushed cover on every rescan while the file was EBOK). Only a fresh catalog row (delete + re-ingest) reliably refreshes a tile.
triggerUpdate moved services on 5.19. It lives on com.lab126.scanner now; com.lab126.ccat triggerUpdate returns lipcErrNoSuchProperty. The daemon calls both (each is a muted no-op where absent).

What ships in Folio

Library::KindlePrep builds a prepared delivery copy per queued book: joint-mobi transcode for AZW3 sources (with byte-patch fallback if the transcode fails), ebook-meta --cover when the source lacks an embedded cover (before the identity rewrite — ebook-meta re-adds a calibre uuid), then the in-place EXTH rewrite across all MOBI headers. Auto-conversions target joint mobi directly (EnsureKindleFormatJob). The daemon handles deliverable renames (old file removed, catalog row dropped, shared-stem sidecar keeps the position). Verified end-to-end 2026-07-12: five delivered books, five real covers, indistinguishable from store books.
