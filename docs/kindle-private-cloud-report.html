Kindle Private Cloud Notes

Status report for replacing Amazon-side Kindle behavior with a self-hosted, privacy-preserving workflow on a jailbroken Kindle.

Short answer: the safe working path is available now: a self-hosted server plus a Kindle-side agent downloads books into /mnt/us/documents/PrivateCloud, then the normal Kindle Library indexes and opens them. Full stock “remote book appears in Library, searchable, tap to download” is not safely working yet.

What We Learned

Normal local content path

When a supported file is copied or downloaded into /mnt/us/documents, Kindle services do the expected local ingestion:

  1. scanner recognizes the file.
  2. ccat updates /var/local/cc.db.
  3. KPP receives catalog update events.
  4. The Library displays the local item.
  5. A normal sidecar directory appears next to the book.

This is the stable path the current prototype uses.

Stock Amazon cloud/download path

For Amazon-style downloads, the stock UI does more than look at cc.db. A real download involves KPP, CVM/framework services, archive, todo, tmd, content manifests, and KindleContentDownloadManagerApplication.

The captured flow for a real Amazon/cloud item showed manifest downloads, staged files under /mnt/us/documents/Downloads/Items01, and post-processing before the reader opens the book.

Fake remote rows

We tested two fake remote-row approaches:

  1. Add only a private archived row to cc.db Entries.
  2. Add both the cc.db row and a matching ksdk.asset.db Nodes row.

Both approaches made the private item visible/searchable in the stock Library, but tapping the item still failed.

Important: raw fake remote rows are not a safe UX right now. They can trigger Kindle’s fatal application dialog and leave the display on a blank/white surface until UI services are restarted.

Proxy / Intercepting Amazon Traffic

The proxy idea is useful for learning, but it is not the shortest path to a full replacement.

Certificate checks performed

No certificate changes were made. Read-only checks found these trust stores:

  • /etc/ssl/certs/ca-certificates-prod.crt and /etc/ssl/certs/ca-certificates.crt for OpenSSL-style clients.
  • /usr/java/lib/security/cacerts for Java/CVM clients.
  • /var/local/system/certstore.db, which is not really a SQLite DB here; it is a small text marker for installed certificates.

The OpenSSL bundle is a plain certificate bundle, but it lives on the read-only root filesystem. The Java store is a Java KeyStore. The usual passwords checked locally (changeit, amazon, kindle, password) did not verify it. Listing without a password only gives an integrity warning, so modifying it safely would need more care.

Practical implication: adding a proxy CA is probably possible, but should be done as a reversible overlay or bind-mount, not by permanently rewriting root filesystem files. It still may not help if KPP/framework code pins certificates or uses a separate trust path.

What a proxy can help with

  • Observe which hostnames the Kindle contacts during Sync, Library refresh, and download.
  • Measure what actions cause network traffic.
  • Block Amazon endpoints to prevent reading-progress/library uploads.
  • Identify which services need local replacements.

Where a proxy likely fails

  • Most traffic is HTTPS, so a plain proxy only sees destination hostnames, not request bodies.
  • Installing a custom CA for TLS inspection may not be enough if apps pin certificates or use custom trust stores.
  • Even if TLS interception works, requests may contain auth tokens and personal account identifiers. Those should not be logged broadly or stored casually.
  • Amazon content download can involve entitlement checks, signed URLs, manifests, staged files, and DRM. Recreating that exactly is brittle and may cross legal/terms boundaries depending on what is emulated.
  • Replacing Amazon endpoints can break registration, sync, Store, archive metadata, thumbnails, and reader services in non-obvious ways.

Safe proxy scope

A defensible proxy setup for this project should stay inside these boundaries:

  1. Only route your own Kindle through it.
  2. Start with DNS and connection logging, not TLS body capture.
  3. Redact or avoid storing auth headers, cookies, tokens, device serials, and account IDs.
  4. Use blocking and allow/deny lists to stop privacy-sensitive uploads.
  5. Do not attempt to bypass DRM or impersonate Amazon entitlements for Amazon-purchased books.
  6. Use the proxy to map behavior, then implement private flows through our own server and Kindle agent.

Recommended proxy experiment

The first useful proxy experiment is not full MITM. It is a local network observer:

  1. Put the Kindle on a Wi-Fi network whose DNS points to your host.
  2. Run a DNS logger such as dnsmasq or a small Python DNS logger.
  3. Optionally route through a transparent firewall/proxy and log destination IP/port/SNI if available.
  4. Perform one action at a time: manual Sync, open book, change progress, download book.
  5. Compare network activity with the on-device log captures already collected.

This tells us what to block for privacy and where Amazon dependencies live, without trying to clone the entire Amazon backend first.

Local Daemon Architecture

The best next design is a Kindle-side daemon controlled by the self-hosted server and by KUAL. It should avoid raw fake cloud rows and treat the stock Kindle Library as a local-file reader/catalog, not as the remote-download engine.

Daemon responsibilities

  1. Poll or receive a private manifest from the self-hosted server.
  2. Maintain local state: available, downloading, downloaded, failed, deleted, read-state-pending.
  3. Download selected books into /mnt/us/documents/PrivateCloud.
  4. Call com.lab126.scanner reScanFile and com.lab126.ccat triggerUpdate after each download.
  5. Generate a readable/searchable local index document, for example PrivateCloud Library.txt.
  6. Watch sidecar folders under /mnt/us/documents/PrivateCloud/*.sdr for progress/annotation changes.
  7. Sync those private sidecar/progress changes to the self-hosted server.
  8. Optionally enforce privacy policy: block or pause selected Amazon sync/upload paths while private books are active.

How it resolves the sync issue

The daemon makes sync explicit and private:

  • Book availability comes from the self-hosted manifest, not Amazon archive sync.
  • Book download comes from the private server, not Kindle's Amazon content manager.
  • Library ingestion is local Kindle scanner/catalog behavior, which already works.
  • Progress sync is copied from local sidecar files to the private server.
  • Amazon upload paths can be blocked or disabled separately after we map them precisely.

Daemon control model

Controller What it does
KUAL User-facing actions: sync manifest, download next, download selected item, refresh Library, show status.
Self-hosted server Provides manifest, book files, progress API, delete/archive decisions, and possibly remote commands.
Kindle daemon Executes local operations safely: download, checksum, scanner refresh, sidecar sync, policy enforcement.
Stock Kindle Library Only sees normal local files and generated local index documents.

Daemon implementation language

The current shell agent is the right prototype, but the long-lived Kindle daemon should be written in Rust.

Language Fit Reason
Shell Prototype and KUAL glue Already works for sync, download, checksums, and LIPC calls. It becomes fragile for a persistent daemon with retries, state, and concurrent file changes.
Rust Recommended daemon Can ship as a small ARMv7 binary, has strong error handling, good file/network primitives, and does not require a runtime on the Kindle.
Go Possible but heavier Simple deployment, but larger binaries and runtime behavior are less attractive on this device.
Python/Node Not recommended on Kindle Good on the server side, but relying on those runtimes on the Kindle adds avoidable footprint and dependency risk.
C Possible but slower to make safe Small binaries, but more manual memory/error handling than needed for this project.

The practical split is: Rust for the daemon, Python for the self-hosted server prototype, shell for install scripts, KUAL entry points, and recovery commands.

The Rust daemon should start small: manifest polling, local state file, book download, checksum verification, atomic publish into /mnt/us/documents/PrivateCloud, scanner/catalog refresh, sidecar polling, sidecar upload/download, and optional network block-rule management.

What not to do

  • Do not inject tappable fake remote rows as the normal UX.
  • Do not blindly disable all todo processing; it may break unrelated device behavior.
  • Do not depend on TLS MITM as the main replacement strategy.
  • Do not log auth tokens or full Amazon request bodies unless there is a narrow, temporary, redacted debugging reason.

Progress And Reading State

Read-only checks found the relevant pieces:

  • Private/local books create sidecar folders such as remote-only-test.sdr.
  • Progress-related files include .mbp1 and sometimes .mbs.
  • /var/local/wsync.db has DataSetProperties, SyncRecords, and DirectoryInfo.
  • Manual Sync triggers BookReadStates, legacy.UPLOAD.MESG, legacy.UPLOAD.SNAP, and whispersync.upload.
  • For local private documents, logs repeatedly said ContentReadStateWhispersyncController: Not putting record to whispersync db, which is encouraging, but manual Sync still schedules generic uploads.

Recommended progress plan

  1. For private books, treat .sdr sidecar files as the source of truth.
  2. Have the daemon detect sidecar changes with polling first; inotify can come later if available/reliable.
  3. Upload sidecar deltas or whole small sidecar files to the private server.
  4. On another Kindle, download the book first, then restore the matching sidecar before opening.
  5. Use network/proxy blocking to prevent Amazon reading-state uploads if needed, but avoid disabling broad services until the exact effect is tested.

Cross-device private progress sync

To sync position from one jailbroken Kindle to another, the daemon should copy private sidecar state through the self-hosted server instead of using Amazon WhisperSync.

  1. The server manifest gives every private book a stable book_id.
  2. Kindle A downloads the book into /mnt/us/documents/PrivateCloud and reads normally.
  3. The reader writes progress/annotation state into /mnt/us/documents/PrivateCloud/<book>.sdr/.
  4. The daemon detects changed sidecar files, initially by polling mtimes and sizes.
  5. The daemon uploads a compact sidecar bundle to the private server under book_id plus a device/profile id.
  6. Kindle B downloads the same book, lets the reader/scanner create the normal local entry, then restores the latest sidecar bundle before opening the book.
  7. The daemon keeps a local backup before overwriting any sidecar, so bad sync can be rolled back.

The first conflict rule can be simple: latest modified sidecar wins. A later version should keep per-device versions on the server and expose conflicts when two Kindles read the same book offline.

This design preserves the stock reading interface while moving the private read-state protocol entirely to the self-hosted server.

Where Amazon Calls Can Be Blocked Or Replaced

Yes: blocking can happen at multiple layers. The right design is usually layered, not a single global block. The daemon should replace the user-facing behavior, while lower layers prevent privacy leaks.

Layer Examples on this Kindle What it can do Risk
Network routing/firewall iptables, default route, DNS server in /etc/resolv.conf Block or redirect outbound Amazon connections. Good for privacy enforcement and endpoint discovery. Medium. Can break registration, Store, archive sync, covers, time, weblabs, and metrics if too broad.
DNS Kindle currently uses LAN DNS 192.168.1.1 Resolve selected Amazon hostnames to a local server or NXDOMAIN. Good for coarse blocking. Medium. Hostnames may be shared across multiple services, and HTTPS cert validation still applies.
TLS trust/certs /etc/ssl/certs/ca-certificates-prod.crt, /usr/java/lib/security/cacerts Can allow a local TLS proxy to inspect/serve traffic if the client trusts the CA and does not pin certs. High. Java store password is not known yet, root FS is read-only, and certificate pinning may still block it.
LIPC/DBus service controls com.lab126.todo, com.lab126.archive, com.amazon.kindlecontentdownloadmanager Pause/schedule some sync tasks or invoke local refresh/download operations. Medium to high. Some controls are broad; disabling todo can affect unrelated jobs.
ToDo topic handling legacy.UPLOAD.MESG, legacy.UPLOAD.SNAP, whispersync.upload, archive.sync Most precise conceptual place to block upload/sync work before network transfer. High until mapped. Handlers are registered through Amazon framework/KAF registries and may be brittle to patch.
Registry/service routing /var/local/reg/*.db, /var/local/root/sysreg.db, prereg DBs In theory, rebind handlers or app associations to local replacements. High. Wrong entries can break app launch and framework behavior.
Catalog/local file layer /mnt/us/documents/PrivateCloud, scanner, ccat, cc.db Safe replacement path: private daemon downloads locally, then stock Library sees local files. Low. This is the path already proven to work.

Recommended layered blocking model

  1. Replacement layer: the local daemon handles private library sync, downloads, and progress upload to your server.
  2. Catalog layer: Kindle only receives normal local files and local generated index documents. No fake tappable remote rows.
  3. Progress layer: daemon watches .sdr sidecars and syncs them privately.
  4. Network layer: DNS/firewall blocks known Amazon upload/sync endpoints once mapped.
  5. Service layer: only if needed, selectively pause or suppress todo topics related to upload/sync. Avoid broad permanent disableToDo unless tested.

Why not only redirect Amazon calls?

Redirecting Amazon calls to our server sounds clean, but the Kindle expects Amazon-specific authentication, endpoint schemas, signed URLs, service-specific response formats, and sometimes content-manager side effects. A custom server would have to mimic a large moving target. A local daemon is simpler: it owns the private protocol and uses stable local Kindle mechanisms to refresh the Library.

Concrete next checks before blocking

  1. Run DNS/SNI observation during manual Sync and private reading sessions.
  2. Classify endpoints into: required for device basics, store/archive, progress upload, metrics, covers/thumbnails.
  3. Test blocking one category at a time with quick rollback.
  4. Confirm whether local private documents really avoid wsync.db records, since logs showed Not putting record to whispersync db for local content.
  5. Only then add persistent block rules or daemon-managed temporary block rules.
