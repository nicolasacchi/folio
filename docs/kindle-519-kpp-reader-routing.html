Kindle 5.19 reader routing: the modern (KPP) reader and how to pin it

Established empirically on a real Kindle (firmware 5.19.2, Photon/KPP UI) on 2026-07-13 via SSH: strings/javap decompilation of the firmware's Java reader stack, inspection of the on-device weblab cache and marker files, and .sdr sidecar fingerprinting to observe which reader actually opened each book. The short version:

A reflowable book opens in the modern reader only when TWO gates are both on: (1) the marker file /var/local/ENABLE_KPPREADER exists, AND (2) Amazon's LegacyFormatMigration weblab (KINDLE_FEATURE_1308000, in the MobileWeblab subsystem) is T1. With both on, books open in the native kfxreader KPP reader (back/home buttons, page numbers). If either is off, the same book opens in the legacy Java reader (YJReader), whose 5.19 chrome has none of that. Our joint MOBI6+KF8 files are format-eligible (BookType is not Mobi7) — the file is never the problem.
Correction to an earlier draft of this note. The marker alone is necessary but not sufficient. This device had ENABLE_KPPREADER present yet books still opened legacy, because gate (2) — the MobileWeblab treatment for KINDLE_FEATURE_1308000 — was C. Also, the KRDS .azw3r/.azw3f sidecars are NOT proof of KPP rendering: KPP shadow mode dual-writes them for position tracking even while the legacy reader draws the page. The only reliable signal is the framework log (isKPPLegacyFormatMigrationEnabled = true/false, Init with (KPP|Java)Reader).

Two readers in one firmware

The reader is the Java "booklet" framework (cvm / concierge Framework, /etc/upstart/framework). Its classpath carries both readers:

Modern — KPP readerLegacy — Java reader
Binary/usr/bin/kfxreader (native C++, runs as a service kfxreader -l)YJReader-impl.jar + MobiReader-impl.jar (in-process Java)
Chromeback arrow, home, page numbers, time-in-chapter, TOC, sticky notesnone of that on 5.19
Metricis_opened_by_kpp_reader = Yes= No
Sidecar it writes.azw3r / .azw3f (KRDS).mbp1 / .mbs (legacy)

For a mobi book the Java framework decides, per book, whether to render it in-process (legacy) or proxy it to the native KPP reader over LIPC (com.lab126.kppReader, MobiKPPReaderController — "Open book by KPP Reader").

The decision chain (decompiled)

Three layers, all in ReaderSDK-impl.jar / MobiReader-impl.jar / Reader-utils.jar:

1. Device switch — KPPReaderSwitchUtils

RZ():  new File("/var/local/ENABLE_KPPREADER").exists() ? KPP_READER : JAVA_READER
Sa():  return new File("/var/local/DISABLE_KPPREADER_WEBLAB").exists()   // true ⇒ ignore the weblab
Sc():  create /var/local/KPPREADER_YJOP_DIALED_DOWN                      // "dial down" legacy for reflowable

Five 0-byte markers live in /var/local: ENABLE_KPPREADER, DISABLE_KPPREADER_WEBLAB, KPPREADER_TRIGGERED, KPPREADER_YJOP_DIALED_DOWN, KPPREADER_YJOP_SB_DIALED_UP. Their presence is the state — content is irrelevant.

2. Per-book gate — MobiBookController.nu()

if (controller == null && ReaderUtils.Z(book))
    controller = new MobiKPPReaderController(...);   // KPP path
return controller;                                   // else → legacy MobiBookViewer

A mobi opens in the modern reader iff ReaderUtils.Z(book) returns true.

3. Eligibility — ReaderUtils.Z(book)

Z(book) = aKA() && ( (cl(book) && !co(book))   // reflowable text (our books)
                     || cG(book)                // fixed-format / manga  (gated by aKB/aKC/aKD)
                     || cK(book)                // other                 (gated by aKM)
                     || (p(book) && aKN()) )     // periodicals           (gated by aKN)
  • aKA() = "isKppReaderEnabled()" — reads /var/local/ENABLE_KPPREADER (cached per framework process). This is the master gate.
  • p(book) = "BookType is not Mobi7" (reads BookMetadata.getContentType()).
  • aKN/aKM/aKB/aKC/aKD = per-category feature gates, each backed by a KINDLE_FEATURE_* weblab (e.g. periodicals = KINDLE_FEATURE_1342385).

Beyond the master gate aKA(), the reflowable path also consults isKPPLegacyFormatMigrationEnabled(), which reads weblab KINDLE_FEATURE_1308000 (name LegacyFormatMigration) from the MobileWeblab client — not the KWIS kindleforeink_weblabs.json cache. On this device that treatment is C, so a reflowable KF8 book stays in the legacy reader even with the marker on. The sibling categories (fixed-format, manga) already read T1; reflowable is a later stage of the same rollout.

The weblab machinery (why it flips)

KPPReaderSwitchManagerImpl registers four KINDLE_FEATURE weblabs (one per content class: reflowable "YJOP", fixed-format "YJFF", manga, sample-book) via the KSDK WeblabManager. Treatment T1 ⇒ "Init with KPPReader", C ⇒ "Init with JavaReader". Assignments are fetched from Amazon and cached on device:

ThingWhere
Weblab cache (244 assignments, plain JSON)/var/local/kindleforeink_weblabs.json
Weblab client id/var/local/mobile_weblab_cid.txt
Fetch endpoint (KWIS)https://kwis-opf.amazon.com/getWeblabs/
Fetch endpoint (MobileWeblab)https://msh<REGION>…/mwl/ (from appreg.db)

Two separate weblab systems coexist: KWIS (the kindleforeink_weblabs.json cache above) and MobileWeblab (com.lab126.kaf.MobileWeblabService, its own store). The reader's reflowable-migration gate (KINDLE_FEATURE_1308000) is read from MobileWeblab. Editing the KWIS JSON — even though it also contains a 1308000 row — does not change what the reader sees. A book-open re-evaluates these gates each time, so behaviour tracks whatever treatment the respective client currently holds.

The reliable signal: the framework log

Ignore the sidecars for reader identity (shadow mode taints them). The authoritative source is /var/log/messages, written by cvm on every book open:

ReaderUtils: isKppReaderEnabled() check for /var/local/ENABLE_KPPREADER is cached = true
MobileWeblabLogUtils: Fetching weblab for experiment : KINDLE_FEATURE_1308000
ReaderUtils: isKPPLegacyFormatMigrationEnabled() check for LegacyFormatMigration = false   ← blocker
ReaderUtils: BookType is not Mobi7                                                          ← file is fine

Gate 1 (marker) reads true; gate 2 (MobileWeblab 1308000) reads false → the reflowable book opens in the legacy reader, no buttons. The daemon reports this to Folio as reader_mode = "kpp_pending".

How to pin the modern reader

  1. Gate 1 (in our control): ensure /var/local/ENABLE_KPPREADER exists and make it immutable (chattr +i) so nothing deletes it; keep /var/local/DISABLE_KPPREADER_WEBLAB too. Persists across reboots. Revert with chattr -i then delete.
  2. Gate 2 (Amazon's): KINDLE_FEATURE_1308000 = T1 in MobileWeblab. There is no marker bypass for it; it arrives via Amazon's staged rollout. A local MobileWeblab override (weblab_overrides/KINDLE_FEATURE_1308000 containing T1) is plausible but was never initialised on this device and is not confirmed to be honoured on a production build.
Editing the KWIS kindleforeink_weblabs.json does nothing for the reader. That file is the KWIS cache; the reader reads 1308000 from the separate MobileWeblab client. Two distinct weblab systems live on the device — don't confuse them.

Freezing experiments — and the tension with the reader

"Freeze experiments" (make kindleforeink_weblabs.json immutable + iptables-REJECT the kwis-opf fetch by TLS SNI) pins the KWIS-driven experiments against silent A/B changes. But it is in direct tension with getting the reader buttons: the change that turns them on (1308000 → T1) is itself an Amazon experiment we want. Freezing/blocking would lock in the current "off".

Resolution on this device: pin the reader (gate 1, immutable) but leave freeze OFF so MobileWeblab can still deliver 1308000 = T1 when Amazon rolls it out. The buttons then appear with no further action. The Folio Freeze experiments toggle stays available per-device for cases where you'd rather lock behaviour than accept a wanted rollout.

Folio integration (shipped)

Both levers are managed device settings, controlled from the web UI rather than an SSH poke — applied on-device 2026-07-13, then wired into Folio:

  • Applied on device — gate 1 pinned: ENABLE_KPPREADER + DISABLE_KPPREADER_WEBLAB made immutable (chattr +i, survives reboots). Freeze relaxed: the weblab cache is un-frozen and the kwis-opf block removed, so Amazon can still deliver 1308000 = T1. Originals backed up under /mnt/us/privatecloud/kpp-backup-<ts>/.
  • Server — per-device flags modern_reader_pinned / freeze_experiments ride the manifest as device_settings; for this device pin=on, freeze=off. The daemon reports reader_mode (kpp / kpp_pending / legacy) + experiments_frozen back via device/status.
  • kindled ≥ 0.2.2 — hardening.rs reconciles every pass (idempotent, quiet): pins/immutabilises or removes the markers, freezes/unfreezes the cache and applies/removes the SNI block per policy, and reads the real gate-2 state from /var/log/messages to report kpp vs kpp_pending honestly.
  • Web UI — the device page shows the true reader state ("modern reader pinned — waiting on Amazon's rollout") with toggles.
Current posture: reader pinned (persists via immutability), freeze off (so the wanted rollout can arrive). When Amazon flips 1308000 → T1, the next book-open logs LegacyFormatMigration = true, the daemon reports kpp, and the buttons appear — no further action.

Traps discovered

The marker is checked once and cached per framework process. aKA() caches ENABLE_KPPREADER's presence at first use ("… is cached ="). Creating the marker takes effect on the next framework start (reboot / restart framework), not mid-session.
Every content class has its own MobileWeblab gate. Reflowable (1308000), fixed-format, manga and periodicals each gate on a distinct KINDLE_FEATURE_* treatment. So the marker being on does not imply any book opens in KPP — each category flips only when its own weblab is T1. On this device reflowable is the last one still C.
No conflict with the cover-tile fix. The joint MOBI6+KF8 container required for Library cover tiles still classifies as "not Mobi7" to the reader (it opens the KF8 half), so it stays KPP-eligible. Both fixes hold at once — verified on Io, la giraffa.
